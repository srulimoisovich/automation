# Лабораторная работа №3. Автоматизация запуска скрипта с помощью cron

## Цель работы

Научиться настраивать планировщик заданий cron для автоматического запуска скриптов. Для этого скрипт получения курса валют из лабораторной работы №2 запускается по расписанию внутри Docker-контейнера, а весь вывод заданий собирается в файл `/var/log/cron.log`.

## Задание

1. В репозитории `automation` создать ветку `lab03` и каталог `lab03`, скопировать в него файлы лабораторной работы №2.
2. Создать файл `cronjob` с двумя заданиями для скрипта `currency_exchange_rate.py`:
   - ежедневно в 06:00 получать курс MDL к EUR за предыдущий день;
   - еженедельно по пятницам в 17:00 получать курс MDL к USD за предыдущую неделю.
3. Создать `Dockerfile` на основе Ubuntu или официального образа Python, который:
   - устанавливает cron, Python и нужные библиотеки;
   - копирует в образ скрипт, файл `cronjob` и скрипт запуска (entrypoint);
   - настраивает cron на выполнение заданий из `cronjob`;
   - запускает cron при старте контейнера;
   - записывает вывод заданий в `/var/log/cron.log`.
4. Создать `docker-compose.yml`, который собирает образ и запускает контейнер.
5. Описать в `readme.md` сборку и запуск, проверку работы cron и структуру проекта.

## Используемые технологии

- **cron** - стандартный планировщик заданий Linux. Каждую минуту он проверяет расписание и запускает команды, время которых наступило.
- **Docker** - контейнер изолирует cron, Python и скрипт от основной системы.
- **Docker Compose** - описывает параметры запуска контейнера (переменные окружения, каталог с результатами, адрес хоста) в одном файле.
- **Ubuntu 24.04** - базовый образ. Его прямо называет задание, и в нём есть все нужные пакеты.
- **Python 3 и python3-requests** - интерпретатор и библиотека для HTTP-запросов из репозитория Ubuntu.

Почему библиотека `requests` ставится через `apt`, а не через `pip`: в Ubuntu 24.04 системный Python помечен как «внешне управляемый» (PEP 668), и команда `pip install` без виртуального окружения завершается ошибкой `externally-managed-environment`. Пакет `python3-requests` из репозитория Ubuntu имеет версию 2.31.0, поэтому условие из `requirements.txt` (`requests>=2.31`) выполняется. Проверка внутри контейнера:

```
$ docker compose exec currency_rates python3 -c "import requests; print(requests.__version__)"
2.31.0
```

Можно было взять образ `python:3.12-slim` и `pip install -r requirements.txt`. Там `pip` работает без ограничений, но задание отдельно упоминает Ubuntu, поэтому выбрана она.

### cronjob

Файл заданий в системном формате `/etc/cron.d`. В отличие от пользовательского `crontab`, в каждой строке после пяти полей времени указывается пользователь, от имени которого выполняется команда (здесь `root`). При старте контейнера `entrypoint.sh` копирует файл в `/etc/cron.d/currency_rates`.

В начале файла задана переменная cron с адресом сервиса:

```
SERVICE_URL=http://host.docker.internal:8080
```

Ежедневное задание:

```
0 6 * * * root /usr/bin/python3 /lab03/currency_exchange_rate.py -f MDL -t EUR -d "$(date -d '-1 day' +\%F)" -u "$SERVICE_URL" >> /var/log/cron.log 2>&1
```

- `/usr/bin/python3` указан полным путём, потому что у заданий cron очень короткий `PATH` (`/usr/bin:/bin`);
- `date -d '-1 day' +\%F` вычисляет вчерашнюю дату в формате ГГГГ-ММ-ДД;
- `>> /var/log/cron.log 2>&1` дописывает в журнал и обычный вывод, и сообщения об ошибках.

Еженедельное задание записано семью строками с одинаковым временем `0 17 * * 5`, по одной на каждый день прошлой недели. Перед каждой строкой есть комментарий, за какой день она запрашивает курс:

```
# 7 дней назад: пятница прошлой недели
0 17 * * 5 root /usr/bin/python3 /lab03/currency_exchange_rate.py -f MDL -t USD -d "$(date -d '-7 day' +\%F)" -u "$SERVICE_URL" >> /var/log/cron.log 2>&1
...
# 1 день назад: четверг
0 17 * * 5 root /usr/bin/python3 /lab03/currency_exchange_rate.py -f MDL -t USD -d "$(date -d '-1 day' +\%F)" -u "$SERVICE_URL" >> /var/log/cron.log 2>&1
```

Все семь строк cron запускает одновременно, поэтому их результаты могут попасть в `cron.log` в любом порядке. Цикл в одной строке был бы короче, но так по файлу сразу видно, какой день запрашивает каждая команда.

### Dockerfile

Перед каждой инструкцией стоит комментарий. Основные шаги:

```dockerfile
FROM ubuntu:24.04
ENV DEBIAN_FRONTEND=noninteractive
RUN apt-get update && apt-get install -y --no-install-recommends cron python3 python3-requests tzdata procps && rm -rf /var/lib/apt/lists/*
WORKDIR /lab03
COPY currency_exchange_rate.py requirements.txt ./
COPY cronjob ./cronjob
COPY entrypoint.sh /entrypoint.sh
RUN chmod +x /entrypoint.sh
ENTRYPOINT ["/entrypoint.sh"]
```

- `DEBIAN_FRONTEND=noninteractive` нужен, чтобы пакет `tzdata` не спрашивал часовой пояс во время сборки;
- `tzdata` содержит файлы часовых поясов, без него нельзя установить `Europe/Chisinau`;
- `procps` добавлен для команды `ps`, которой проверяется, что cron запущен;
- `--no-install-recommends` и удаление `/var/lib/apt/lists` уменьшают размер образа.

### entrypoint.sh

Скрипт основан на примере из задания. Функции `create_log_file`, `monitor_logs` и `run_cron` сохранены, сообщения переведены на русский, и добавлены две функции:

- `set_timezone` - берёт часовой пояс из переменной `TZ` (по умолчанию `Europe/Chisinau`), делает `/etc/localtime` ссылкой на нужный файл зоны и записывает имя пояса в `/etc/timezone`;
- `install_cronjob` - копирует `/lab03/cronjob` в `/etc/cron.d/currency_rates` и выставляет права `0644`. Cron пропускает файлы в `/etc/cron.d`, если в них может писать кто-то кроме владельца-root.

Порядок действий:

```sh
set_timezone
env > /etc/environment
create_log_file
install_cronjob
monitor_logs &
run_cron
```

Строка `env > /etc/environment` важна: cron запускает задания с почти пустым окружением и не видит переменные контейнера. Модуль `pam_env` при запуске каждого задания читает `/etc/environment`, поэтому ключ `EXCHANGE_API_KEY` доходит до скрипта. `exec cron -f` делает cron главным процессом контейнера, а `tail -f` в фоне выводит журнал в `docker compose logs`.

### docker-compose.yml

```yaml
services:
  currency_rates:
    build: .
    container_name: currency_rates_cron
    environment:
      EXCHANGE_API_KEY: EXAMPLE_API_KEY
      TZ: Europe/Chisinau
    extra_hosts:
      - "host.docker.internal:host-gateway"
    volumes:
      - ./data:/lab03/data
```

- `EXCHANGE_API_KEY` - ключ API, который скрипт из лабораторной работы №2 читает из окружения;
- `TZ` - часовой пояс для `set_timezone`;
- `extra_hosts` добавляет имя `host.docker.internal`. В Docker Desktop оно есть и так, а на Linux без этой строки его нет;
- том `./data:/lab03/data` нужен, чтобы JSON-файлы с курсами появлялись на хосте в `lab03/data/`;
- политика перезапуска не задана: контейнер запускается вручную для проверки.

Контейнер обращается к сервису через порт 8080 хоста. Другой способ - подключиться к внешней сети `lab02prep_default` и использовать адрес `http://web`. Я выбрал `host.docker.internal`, потому что тогда файл `cronjob` не зависит от имени проекта `lab02prep` и его сети.

## Разбор расписания cron

Строка расписания состоит из пяти полей времени:

| Поле | Значения | `0 6 * * *` | `0 17 * * 5` |
|---|---|---|---|
| минута | 0-59 | `0` | `0` |
| час | 0-23 | `6` | `17` |
| день месяца | 1-31 | `*` (любой) | `*` (любой) |
| месяц | 1-12 | `*` (любой) | `*` (любой) |
| день недели | 0-7 (0 и 7 - воскресенье) | `*` (любой) | `5` (пятница) |
| итог | | каждый день в 06:00 | каждую пятницу в 17:00 |

Какие даты запросит еженедельное задание в пятницу 2026-10-23 (проверено командой `date -d "2026-10-23 -N day" "+%F %A"` в контейнере):

| Сдвиг | Дата | День недели |
|---|---|---|
| `-7 day` | 2026-10-16 | пятница |
| `-6 day` | 2026-10-17 | суббота |
| `-5 day` | 2026-10-18 | воскресенье |
| `-4 day` | 2026-10-19 | понедельник |
| `-3 day` | 2026-10-20 | вторник |
| `-2 day` | 2026-10-21 | среда |
| `-1 day` | 2026-10-22 | четверг |

Почему `\%`: для cron знак `%` внутри команды служит концом строки, и всё, что стоит после первого `%`, уходит команде на стандартный ввод. Поэтому в `cronjob` формат даты записан как `+\%F`: cron убирает обратную косую черту и передаёт оболочке обычный `+%F`. Это правило действует только внутри файла заданий. Когда та же команда запускается вручную через `docker compose exec ... sh -c '...'` (шаг 4 проверки), её читает обычная оболочка, и там пишется просто `+%F`, без обратной косой черты.

Почему используется `SERVICE_URL`. Адрес сервиса передаётся не через docker-compose.yml, а через переменную SERVICE_URL в файле cronjob и параметр -u, потому что скрипт из лабораторной работы №2 не читает адрес из переменных окружения: адрес задаётся только параметром -u (--url). Через docker-compose.yml передаётся только ключ EXCHANGE_API_KEY.

Все семь запросов прошли, и в `data/` появилось семь файлов `MDL_to_USD_2025-08-22.json` ... `MDL_to_USD_2025-08-28.json`. Курс за субботу и воскресенье (23 и 24.08) совпадает с пятничным, а курс за 27.08 (День независимости, нерабочий день) - с курсом за 26.08: в нерабочие дни новый курс не устанавливается.

**6. Возврат исходного расписания.** Временные строки есть только внутри контейнера. Пересоздаём контейнер, и `entrypoint.sh` снова устанавливает исходный `cronjob`:

```bash
docker compose up -d --force-recreate
```

После этого в `/etc/cron.d/currency_rates` снова 9 строк без комментариев (`SERVICE_URL`, одно ежедневное и семь еженедельных заданий).

## Почему в журнале ошибки диапазона дат

Учебный сервис `lab02prep` знает курсы только за период с 2025-01-01 по 2025-09-15, а cron берёт даты из настоящего календаря. Вот какие даты задания получили бы в эти дни:

| Задание | Запуск | Запрашиваемые даты | Входят в 2025-01-01 — 2025-09-15? |
|---|---|---|---|
| ежедневное, MDL -> EUR | суббота 2026-10-24 | 2026-10-23 | нет |
| еженедельное, MDL -> USD | пятница 2026-10-23 | 2026-10-16 ... 2026-10-22 (7 дат) | нет, ни одна |

Скрипт из лабораторной работы №2 сравнивает дату с границами периода ещё до обращения к сервису. Если дата не подходит, он печатает сообщение и выходит с кодом 1. Поэтому каждый настоящий запуск по расписанию оставляет в `/var/log/cron.log` такую строку (для еженедельного задания - семь строк, по одной на дату):

```
Ошибка: дата 2026-10-23 выходит за пределы доступного периода (2025-01-01 — 2025-09-15).
```

Я считаю это правильным результатом, а не сбоем настройки: по такой строке видно, что cron запустил задание вовремя, `date` вычислил нужную дату, а вывод дошёл до журнала. Ограничение здесь в данных сервиса. Что те же команды работают с датами из 2025 года, показано в шагах 4 и 5 проверки.


## Выводы

1. Cron в контейнере не видит переменные окружения Docker. Их нужно сохранить в `/etc/environment` при старте (`env > /etc/environment`), тогда `pam_env` передаёт их каждому заданию. Проверка через `env > /tmp/env.txt` показала, что `EXCHANGE_API_KEY` действительно доходит до задания.
2. В строках cron символ `%` нужно экранировать (`\%`), иначе команда обрезается. В обычной оболочке экранирование не нужно.
3. У заданий cron короткий `PATH`, поэтому интерпретатор указан полным путём `/usr/bin/python3`.
4. Файлы в `/etc/cron.d` должны принадлежать root и иметь права `0644`. Установка файла из `entrypoint.sh` с явным `chmod` гарантирует это при каждом запуске.
5. Часовой пояс в контейнере по умолчанию UTC. Пакет `tzdata` и переменная `TZ` нужны, чтобы 06:00 и 17:00 означали местное время Кишинёва.
6. Cron работает по настоящему календарю, поэтому с учебным сервисом (данные только за 2025 год) реальные запуски дают ошибку диапазона. Работоспособность расписания проверена временной строкой `* * * * *` с датой из доступного периода: задание выполнилось, курс записан в журнал, JSON-файл появился на хосте.
